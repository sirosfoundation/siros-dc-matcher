# `zkp_req` presentations

The presentation side of the `zkp_req` draft 0.1 (Sections 3, 4, 4.1 and 6.1), the proof backends'
`Proof`, and the Longfellow and Vega system rulebooks (Sections 3 and 9), rulebook repository commit
`e65861c`. Code: `siros_zkp_req::presentation`, `siros_zkp_req::vp_token`,
`siros_zkp_req::structure` and `siros_zkp_req_nym_auth::verify`. Vectors:
`crates/siros-zkp-req-nym-auth/tests/vectors/presentation/`, generated by
`scripts/gen_zkp_req_presentation_vectors.py`.

## Shape

In a JSON `vp_token`, the entry of the query `id` is an array of strings, each the base64url,
without padding, of a CBOR `ZkpPresentation`. In `direct_post.cwt` each presentation is the map
itself.

```cddl
ZkpPresentation = {
  "system_id"     : tstr,
  "proof_backend" : tstr,
  ? "req_set"     : uint,               ; present exactly when the query has _req_sets
  "proof"         : bstr .cbor Proof,
  "results"       : { * tstr => any }   ; the answered option's return handles
}
Proof = {
  "inputs"   : { "issuer_key_set": [ bstr ], "proof_time": tdate },
  "zk_proof" : bstr
}
```

`issuer_key_set` holds exactly the DER Document Signer certificate of the credential's `x5chain`.
`proof_time` is exactly `YYYY-MM-DDThh:mm:ssZ`. A `pseudonym` result is a 32-byte `bstr`; a
function without a result gives `true`.

## Checks, in order

1. The `vp_token` (`presentations_of`): a JSON object without repeated members, an entry for the
   query, a non-empty array, one element unless the query sets `multiple`, each element unpadded
   base64url.
2. The presentation (`ZkpPresentation::decode`): one strict CBOR item (definite lengths, no
   repeated keys, depth at most 32, nothing after it), a map with exactly the members above.
3. Steps 1 to 5 of Section 4.1 (`answered_option`): the system and the backend are listed, the
   system runs on the backend, `req_set` names an option exactly when the query has `_req_sets`,
   the keys of `results` are the option's handles, and a function without a result gives `true`.
4. The system (`check_presentation`): `Proof` and its `inputs` (`proof_encoding`), one certificate
   with a P-256 key (`issuer_key_set`), the form of `proof_time` (`proof_time`), the Verifier's
   own option within the system's Section 2 (`request`), and a 32-byte pseudonym (`results`).
5. The Verifier (`verify`): `proof_time` within its tolerance (`proof_time`), the certificate
   trusted and valid at its clock (`issuer_key_set`), then the proof against the statement it
   builds from its own request, session and clock (`proof_encoding`, `proof_invalid`,
   `public_input`).
